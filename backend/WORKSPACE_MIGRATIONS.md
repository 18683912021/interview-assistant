# Workspace 数据迁移

应用启动时 `app.db.init_db` 在同一事务中执行尚未登记的迁移，并在 `app_schema_migrations` 记录版本。PostgreSQL 使用事务级 advisory lock，避免多个 API worker 重复执行。升级前应备份数据库；迁移不调用模型、邮件或语音服务。

- `001_workspace_v2`：增加 workspace 会话、简历版本、岗位及设置表，保留所有旧表。
- `003_legacy_interview_history`：一次性把已有账号的旧 `interviews` 记录复制到 workspace，以同一个 UUID 和原账号归属展示。已有同 UUID 的 workspace 记录优先保留，不覆盖其编辑内容。迁移登记后再次启动不会重复导入，因此用户后来删除的 workspace 历史不会复活。旧客户端在此次迁移完成后新增的旧表记录不会自动持续同步。
- `004_deleted_workspace_interviews`：保留已删除会话的 UUID、原账号及删除时间；不保留对话、答案、简历快照或复盘正文。即使客户端丢失首次保存回执，重放 `expected_revision=0` 也不能复活已删除会话；同账号重复删除可安全重试。

历史会话的秒级时间统一为毫秒，已是毫秒的时间保持不变；岗位/标题显示「编程语言 · 历史面试」含义的标签。旧客户端把 AI 气泡插在所选发言之后，因此按保存的原始数组顺序，将 AI 气泡提取为独立参考答案，关联此前最近的一条非 AI 发言；缺少来源时不虚构问题。未结束的 AI 文本标为截断，空的未结束请求标为取消。候选人发言与 AI 参考答案分别保存，便于复盘区分依据。

旧系统未保存采集来源、岗位 JD、原始简历版本时，不能恢复这些信息。采集来源使用兼容默认值 `both`；材料关联留空。旧 `resumes.intro` 是生成后的自我介绍，不作为原始简历导入，用户需重新上传或粘贴真实简历。旧客户端已经截掉的发言也无法恢复。没有对应账号的历史、无效的原始 JSON 和其他原始记录继续保留在旧表；无效 JSON 在新历史中显示为空记录，需管理员从备份/旧表核查。

此迁移只复制历史，不修改余额或扣费，不生成复盘，不删除旧数据。回退应用时原旧表仍在；请勿删除迁移版本标记来尝试重新导入，否则可能把已删除的旧记录再次导入。
