## 零、Electron 基础概念（面试打底 · 补充）

> **【面试速查 · 2026-08-17 补充】** 本节把后文反复出现的名词先解释一遍：每个技术是什么、干什么用的，面试被追问"XX 是什么"时答案从这里拿。全文原有内容未改动，所有补充块都带"补充"标记，面试前觉得啰嗦可以整块删掉。

### 1. Electron 是什么

**一句话：把 Chromium 浏览器内核 + Node.js 运行时打包进一个桌面应用框架，用 Web 技术写跨平台桌面应用。** VS Code、Slack、飞书桌面版都是 Electron。

拆成两半看分工：

- **Chromium（负责界面）**：UI 全部用 HTML/CSS/JS 写，所以 React、Tailwind 这些 Web 技术栈直接可用，不用学 Windows 原生界面开发（Win32/WPF）。
- **Node.js（负责系统能力）**：浏览器沙箱拿不到的能力由它提供——读写文件、spawn 子进程、加载 C++ 插件、调用操作系统 API。

选型判断：**界面想用 Web 写 + 需要浏览器给不了的系统级能力 → Electron**。如果面试官问"和 Tauri 比？"——Tauri 是同赛道竞品（Rust + 系统 WebView），体积更小，但团队技术栈是 Node/TS，Electron 生态和原生插件（node-gyp/N-API）路径更成熟。心里有数即可，不用主动展开。

### 2. 进程模型：主进程 / 渲染进程 / preload（最重要的地基）

Electron 应用启动后跑着多个进程：

- **主进程**：整个应用**只有一个**，跑 Node.js。职责：创建窗口、应用生命周期、系统能力（托盘、快捷键、文件、原生插件）。AudioCaptureManager、LibreOffice 转换、下载器、托盘全在这里。
- **渲染进程**：**每个窗口一个**，跑 Chromium。职责：画界面、处理交互。默认和浏览器页面一样受限——不能碰文件系统、不能加载 C++ 插件。主窗口和浮窗是两个独立的渲染进程，各跑各的 React 应用。
- **preload 脚本**：每个窗口加载页面之前执行的脚本，**唯一能同时接触 Electron 能力（ipcRenderer 等）和 DOM 的位置**，作用是当桥——把主进程允许的能力摆渡给页面。

为什么这样分？这是 Chromium 自带的安全模型：**每个页面独立沙箱，一个页面崩了或被攻破不影响其他页面和主进程**。Node 的强能力全部锁在主进程，渲染进程要什么能力必须走 IPC 申请——这就是第一节、第五节所有架构讨论的出发点。

一个加分认知：**主进程不是渲染进程的"父进程"，它们是平级的操作系统进程，只通过 IPC 消息通信。**

### 3. IPC 是什么

IPC = Inter-Process Communication（进程间通信），**两个进程之间传消息的机制**。Electron 给两侧各一套 API：

- 主进程侧：`ipcMain.handle` 收请求并返回结果；`webContents.send` 主动推消息给某个窗口。
- 渲染进程侧：`ipcRenderer.invoke` 发请求拿 Promise；`ipcRenderer.on` 订阅主进程推来的消息。

两种通信模式（项目里都用）：

- **请求-响应**：invoke → handle → 返回 Promise。"帮我转个文件""LibreOffice 装好了没"这类一问一答。preload 的 fileConvert、storage、window 分类基本全是这种。
- **单向推送**：webContents.send → on。"转写结果来了""下载到 45%"这类主进程主动广播。preload 里所有 onXxx 回调都是这种。

两个底层事实：消息经 Chromium 内部的消息管线（Mojo，Chrome 的 IPC 框架）在本机进程间传递；**载荷会被序列化拷贝**（结构化克隆），不是传引用——所以大对象高频 IPC 有成本，设计时值得注意。

### 4. 安全三件套：nodeIntegration / contextIsolation / contextBridge

第一节讲"为什么用 contextBridge"的前提是这三个默认开关，面试高频：

- **nodeIntegration**：渲染进程能否直接用 Node（require('fs') 等）。默认 false。开 true = 页面里任何 JS（第三方包供应链投毒、XSS 注入的代码）都能读写用户文件、执行系统命令。
- **contextIsolation**：preload 的 JS 上下文与页面的 JS 上下文是否隔离。默认 true。隔离后页面**看不见** preload 里 require 的模块和变量，只能拿到 contextBridge 显式摆渡的东西——就算页面被 XSS 打穿，攻击者也摸不到 Node 能力。
- **contextBridge**：隔离前提下的"合法摆渡"API。`exposeInMainWorld('electronAPI', {...})` 把白名单方法挂到 window.electronAPI。摆渡的只是函数本身，preload 内部的模块引用不会泄漏。

一句话总结：**关 nodeIntegration（默认）、开 contextIsolation（默认）、能力只经 contextBridge 白名单暴露**——这就是 Electron 官方推荐的安全基线，也是 preload.ts 的做法。

### 5. BrowserWindow / webContents

- **BrowserWindow**：Electron 的窗口对象。`new BrowserWindow(options)` 创建窗口，options 决定透明、无边框、置顶等行为（第五节浮窗全靠它）。一个 BrowserWindow = 一个渲染进程。
- **webContents**：窗口里那个页面的句柄（"这个窗口正在渲染的页面"）。主进程靠 `win.webContents.send(channel, data)` 把消息推进指定窗口。注意坑：窗口销毁后再 send 会抛异常——项目里 send 前做了窗口存活判断（ipc-handlers.ts 有注释），这是 Electron 常见崩溃点。

### 6. 原生模块：node-gyp / N-API / node-addon-api

- **.node 文件**：Node 原生插件的产物，本质是编译好的动态库（Windows 上就是 DLL 改了扩展名）。require 它 = 加载一段 C++。
- **node-gyp**：Node 官方的编译工具。读 binding.gyp（编译配置：源文件、头文件、系统库），调本机编译器（Windows 上是 MSVC）把 C++ 编成 .node。项目的 electron/audio/native/binding.gyp 定义了 wasapi_loopback 编译目标。
- **N-API**：Node 官方定义的 C 层 API 规范，ABI 稳定——跨 Node 大版本不用重新编译。
- **node-addon-api**：N-API 之上的官方 C++ 封装库，提供 Napi:: 命名空间（Napi::ThreadSafeFunction 等）。**项目实际用的是它，它底层就是 N-API**——所以面试说"用 N-API 的 ThreadSafeFunction"完全成立。
- **Electron 特有的坑**：Electron 内置的 Node 和系统安装的 Node 的 ABI 不同，插件必须针对 Electron 编译（electron-rebuild / electron-builder 的依赖重编译）。项目的 ensure-native 脚本把这步全自动化了，dev 启动和打包前自动保证插件可用。

## 一、Electron 进程架构（contextBridge + IPC）

**简历对应：** "借助 AI 辅助完成 Electron 主进程架构搭建，采用 contextBridge + IPC 隔离渲染进程与主进程，设计 preload API 分层暴露音频控制、文件转换、窗口管理、本地存储四类能力"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 本节名词的作用说明，原有问答未改动。

- **EventEmitter**：Node 内置的事件发射器。`on('事件名', 回调)` 订阅，`emit('事件名', 数据)` 广播。解决"数据生产者不用知道谁在消费"的解耦问题——AudioCaptureManager 继承它：底层采集线程和网络回调只管 emit，谁要听谁 on，以后加浮窗只是多一个订阅者，采集代码一行不用改。
- **webContents.send / ipcRenderer.on / invoke / handle**：主进程推、渲染进程收、请求-响应四件套，详见第零节 3。
- **onXxx 的返回值**：preload 里每个 onXxx 都返回一个取消订阅函数（内部调 removeListener），组件卸载时调用——防止重复订阅导致同一个回调被触发多次，这是 Electron 渲染层的经典内存泄漏点。
- **XSS（跨站脚本攻击）**：恶意脚本被注入页面并执行。在 Electron 里格外危险：一旦渲染进程被攻破且开了 nodeIntegration，攻击者等于拿到本机权限。contextBridge 白名单的意义就是让 XSS 最多拿到那几十个受限方法。
- **IPC 通道命名**：项目用 `前缀:动词` 约定（audio:start-capture、file:download-libreoffice、window:toggle-overlay、storage:get），和 preload 四分类一一对应。可以说：通道命名就是接口设计，前缀对应职责域。
- **storage 为什么也走 IPC**：渲染进程自己的 localStorage 受浏览器存储策略限制（配额、清理时机不可控），而且主进程侧的托盘、窗口逻辑也要读同一份配置。走 IPC 存主进程文件系统，两侧共享同一数据源，可控性更强。

### 1. 为什么选 Electron 而不是直接用 Web？

**业务层面：** 桌面端需要有系统音频采集能力——浏览器里的 Web Audio API 只能拿麦克风，拿不到系统播放的声音（比如对方在视频会议里说话的声音）。Electron 可以通过 C++ 原生插件直接调用 Windows WASAPI，这是纯 Web 做不到的。

**产品层面：** 桌面端需要浮窗置顶、全局快捷键、系统托盘、ContentProtection 隐身——这些都是操作系统级能力，浏览器沙箱做不了。

### 2. 为什么用 contextBridge + IPC，而不是开 nodeIntegration？

**安全。** 如果开启 nodeIntegration，渲染进程里的任何 JS 代码（包括第三方 npm 包、XSS 注入）都能直接读写用户文件、执行系统命令，风险极大。

我用 contextBridge 的 exposeInMainWorld 方法在 preload 脚本里精确控制暴露哪些 API。渲染进程只能通过 window.electronAPI 这个命名空间调用我定义好的方法，而 preload 有独立的 JS 上下文，和渲染进程的全局变量不共享，天然隔离。这样即便 npm 依赖里混入了恶意脚本，它也拿不到 Node.js 的能力——只能调我限定好的那几十个 API。

### 3. preload API 为什么分四类？

我把 API 按职责分成四个对象：音频控制（audio）、文件转换（fileConvert）、窗口管理（window）、本地存储（storage）。

**思想是按职责分层。** 这四个维度互不干扰，各自管各自的事。后续加新能力，比如加一个"截图"功能，直接在 window 或新开一个分类下面扩展就行，不破坏现有结构。渲染进程调用时语义清晰——想开始采集就叫 `electronAPI.audio.startCapture()`，想切换浮窗就叫 `electronAPI.window.toggleOverlay()`，一看方法名就知道在干什么。

### 4. 主进程如何把音频事件推给渲染进程？

这是 Electron 里常见的"主进程主动推消息"场景。AudioCaptureManager 是一个事件发射器（EventEmitter），主进程监听它的事件，然后通过 `webContents.send` 推到渲染进程。渲染进程不是轮询——轮询是每隔一段时间去问"有数据吗"，低效且延迟大——而是通过 preload 暴露的 onState、onTranscription 等回调被动接收，是事件驱动的 push 模式。

完整链路是：AudioCaptureManager 发出 transcription 事件 → ipc-handlers.ts 调用 mainWindow.webContents.send 发送 IPC 消息 → preload.ts 里用 ipcRenderer.on 监听这个消息 → 渲染进程通过 window.electronAPI.audio.onTranscription 注册的回调收到数据。这条链路上的每一环都可以独立替换——假如要加一个浮窗接收同样的数据，只需要在 ipc-handlers 里多调用一次 overlayWindow.webContents.send。

## 二、WASAPI Loopback C++ 原生插件（node-gyp）

**简历对应：** "编写 C++ WASAPI Loopback 原生插件（node-gyp 编译），实现 Windows 系统音频采集"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** COM/WASAPI 链路的名词解释，原有问答未改动。

- **COM（Component Object Model）**：Windows 的二进制组件标准。核心思想：**接口与实现分离**——调用方只面向接口编程，实现可以是任何 DLL；所有 COM 对象都继承 IUnknown 接口，用引用计数（AddRef/Release）管理生命周期。**WASAPI 的全部 API 都是 COM 接口**，所以第一步必须初始化 COM 运行时。
- **CoInitializeEx**：告诉 Windows"这个线程要使用 COM 了"，并声明线程模型。COINIT_MULTITHREADED 表示这个线程可以并发调用 COM；单线程模型（STA）要求所有调用排队。采集线程独立运行、没有界面消息循环，用 MTA 合适。
- **IMMDeviceEnumerator**：设备枚举接口——"系统里有哪些音频设备"。
- **IMMDevice**：代表一个具体音频设备（"这块声卡"），它的 Activate 方法能激活出各种功能接口。
- **IAudioClient**：WASAPI 核心接口，负责**建立音频流**——设置格式（48kHz/立体声/浮点）、共享/独占模式、缓冲区大小。是"配置层"。
- **IAudioCaptureClient**：从已建立的流里**取数据**的接口——GetNextPacketSize 查有没有新包，GetBuffer 拿 PCM。是"取数层"。
- **共享模式 vs 独占模式**：共享模式下所有应用共用声卡，经 Windows 音频引擎混音；独占模式绕过混音器直连硬件，延迟最低但会霸占设备（其他应用没声音）。Loopback 要抓混音结果，只能在共享模式下工作。
- **PCM（脉冲编码调制）**：未压缩的原始音频格式——以固定频率采样，每次把波形幅度量化成数字。MP3/AAC 播放前都要先解码成 PCM，Windows 混音器处理的就是 PCM，所以 Loopback 抓到的是"最终要进扬声器的那份数据"。
- **v8**：Chromium/Node 的 JavaScript 引擎。JS 代码只能跑在 v8 管理的线程上，C++ 线程直接调 JS 是未定义行为（可能直接 crash）——这就是必须用 ThreadSafeFunction 的原因。
- **ThreadSafeFunction（补充细节）**：本质是**线程安全的任务队列**——采集线程往队列塞"调用 JS 回调"的任务，Node 事件循环在自己线程上取出执行，两边永远不直接碰面。项目用 NonBlocking 模式：塞任务永不阻塞采集线程；队列满（64 帧）时丢最新帧而不是卡住——对实时音频"宁可丢也不能停"。
- **node-gyp / binding.gyp / N-API / node-addon-api**：见第零节 6。
- **NAudio**：C#/.NET 生态最流行的音频库。要用它得走 Edge.js 之类的 .NET↔Node 桥接，多一层运行时，太重。
- **Edge.js**：让 Node 和 .NET 互调的桥接库，把 C# 代码跑在独立进程里，集成复杂。
- **SoX / node-record-lpcm16**：SoX 是经典跨平台命令行音频工具；node-record-lpcm16 是 npm 录音包，底层 spawn SoX 子进程，只能"录一段拿结果"，没有实时流式帧回调，做不了帧级低延迟。
- **AUDCLNT_BUFFERFLAGS_SILENT**：WASAPI 给每包数据附带的标志位。系统没声音时仍按节拍吐包（内容全 0），这个标志让程序不用检查数据就知道"这包是静音"——静音帧优化的依据。

### 1. 为什么选 WASAPI Loopback？

**需求：** 桌面端和移动端场景不同。移动端用 MediaProjection 抓设备内部音频（播客、网课、游戏），桌面端需要抓 Windows 系统混音输出——视频会议里对方说话的声音、网页播放的音频、本地播放器放的音乐等，凡是最终从扬声器出来的声音都要抓到。

**技术选型对比：**
- Web Audio API 只能拿麦克风，拿不到系统音频
- Stereo Mix（声卡立体声混音）看驱动支持，很多笔记本声卡根本不支持这个选项
- 虚拟声卡驱动需要安装内核驱动，要买代码签名证书，兼容性和维护成本高
- WASAPI Loopback 是 Windows Vista 之后原生提供的接口，不需要装驱动，不需要用户额外配置

WASAPI Loopback 的工作原理是：Windows 音频引擎把各个音源（浏览器、播放器、VoIP 软件）混好之后，在送到扬声器之前，Loopback 模式可以在这条路径上截取 PCM 数据。所以不管源头是什么应用发出的声音，只要最终经过 Windows 混音器，就能抓到。

### 2. C++ 插件怎么写的？

整个流程分六步：

第一步，**初始化 COM 运行时**。WASAPI 是 COM 接口，必须在调用之前用 `CoInitializeEx` 初始化，参数选择多线程模式（COINIT_MULTITHREADED），因为音频采集跑在独立线程上。

第二步，**枚举设备**。用 `IMMDeviceEnumerator` 获取系统中的默认渲染设备——也就是当前 Windows 正在使用的扬声器输出设备。

第三步，**激活 AudioClient 接口**。调用 `IMMDevice::Activate` 拿到 `IAudioClient` 对象，然后用 `Initialize` 方法初始化，关键参数：共享模式、Loopback 模式、缓冲区大小设为 1 秒。

第四步，**获取采集客户端**。通过 `GetService` 方法拿到 `IAudioCaptureClient` 接口，这是实际的音频数据来源。

第五步，**启动采集线程**。创建一个独立的 C++ 线程，循环调用 `GetNextPacketSize` 检查有没有新数据，有数据就用 `GetBuffer` 拿到裸 PCM 数据，处理完释放缓冲。

第六步，**跨线程回调到 Node.js**。C++ 采集线程不能直接调用 JS 函数——JS 只能在 Node.js 的主事件循环线程运行。所以用 N-API 提供的 `ThreadSafeFunction`，把 PCM 数据安全地排队到事件循环中，由主线程度调 JS 回调函数。

### 3. 为什么用 N-API 而不是 node-addon-api 的其他方式？

N-API 是 Node.js 官方的稳定 ABI 层，跨 Node 大版本兼容——比如用 N-API 写的插件，从 Node 18 升到 Node 22 不需要重新编译。而 `ThreadSafeFunction` 是解决跨线程调 JS 的关键能力：C++ 采集线程和 Node.js 主线程不在同一条线程上，直接用 v8 API 调 JS 是未定义行为，ThreadSafeFunction 帮我做了这个排队和同步。

### 4. 为什么不直接用第三方库？

- **NAudio** 是 C# 的，Electron 集成要走 Edge.js 桥接，太重了
- **node-record-lpcm16** 底层调的是 SoX 命令行工具，通过子进程方式获取音频，没有实时的流式回调，无法做到帧级别的低延迟处理

我需要的是每 10 毫秒检查一次，拿到 PCM 数据立即通过 WebSocket 发走——延迟越低越好。自己写 C++ 插件是最可控的方案。

### 5. 静音帧优化

WASAPI 在没有音频播放时，仍然会持续返回数据，只不过全是 0。代码里检查了 `AUDCLNT_BUFFERFLAGS_SILENT` 标志位——当它为真时，说明当前帧全是静音，直接丢弃，不传给 JS 层。这个优化看似简单，实际省了不少 CPU——没声音的时候整条链路都在闲置状态，不做归一化、不编码、不发送。

## 三、PCM 音频管线（归一化 + 帧缓冲）

**简历对应：** "经 PCM 归一化管线统一转为 16kHz 单声道"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 音频基础概念，原有问答未改动。

- **采样率**：每秒采多少个样本点（Hz）。48kHz = 每秒 48000 个点；16kHz = 每秒 16000 个点。采样率决定能还原的最高频率——奈奎斯特定理：最高只能还原采样率一半的频率。语音识别只关心 8kHz 以下的人声频段，16kHz 采样完全够用，多采的全是冗余。
- **位深**：每个样本用多少 bit 表示幅度。16 位 = 65536 个音量级；32 位浮点 = 用浮点数表示幅度，动态范围更大。混音器内部用浮点（精度高），网络传输用 16 位整数（省一半带宽）。
- **声道**：单声道 = 1 条波形；立体声 = 左右 2 条。语音内容左右声道几乎相同，合并成单声道不丢信息。
- **PCM16 LE**：16 位有符号小端整数格式。LE = Little Endian（小端序，低位字节在前）——字节序不统一会导致解码出来全是噪音，所以格式名里必须写清楚（大小端详见第四节速查）。
- **归一化的数据量账**：48kHz 立体声 32 位浮点 = 每秒 384KB；16kHz 单声道 16 位 = 每秒 32KB——数据量直接砍到 1/12。这就是归一化的实际收益。
- **重采样**：改变采样率。48k→16k 是 3:1 降采样，输出样本可能落在两个输入样本之间，所以必须插值。
- **混叠（aliasing）**：最近邻取样的问题所在——直接"台阶化"取点等价于没有滤掉高于新采样率一半的频率，这些频率会"折叠"回低频段，听感发闷、带金属声。线性插值在语音场景误差足够小，且计算量极低；更严格的方案是加窗 sinc 插值（保真最高但计算重），语音用不上。
- **量化噪声**：把连续幅度离散成有限级别产生的舍入误差，表现是轻微底噪。16 位量化噪声约 -96dB，远低于人耳感知，语音场景足够。
- **clamp（限幅）**：插值和 (L+R)/2 可能算出超出 16 位范围的值，硬性截断到 [-32768, 32767]。不做的话值会溢出回绕成爆音。

### 1. 为什么需要归一化？

WASAPI 输出的是声卡混音的原生格式——典型的是 48000Hz、立体声、32 位浮点或者 16 位整数。但后端 ASR 引擎的输入要求是固定的：16000Hz、单声道、PCM16 LE。格式不统一，后端没法处理。归一化的作用就是把任何输入格式都转成这个标准格式。

### 2. 归一化怎么做的？

**重采样用线性插值，不用最近邻。** 比如 48kHz 降到 16kHz，采样率比值是 3.0——理论上每 3 个原始样本取 1 个就好。但如果直接用"每隔 3 个取第 1 个"（最近邻取样），波形会失真，高频部分尤其明显，引入量化噪声。我用线性插值：输出样本的位置如果在两个原始样本之间，就按小数部分的比例做插值——比如输出样本在原始样本位置 5.2，就用 80%×原始样本5 + 20%×原始样本6 来计算。

**立体声转单声道：** 左声道和右声道取平均值 (L+R)/2，保持总能量不变。

**最后 clamp 防溢出：** 值域限制在 -32768 到 32767 之间，保证 PCM16 LE 格式的有效范围。

### 3. 帧累积器（PcmFrameAccumulator）的设计

**为什么帧长固定为 1280 字节？** 1280 字节 = 16000 样/秒 × 2 字节/样 × 0.04 秒 = 40 毫秒一帧。这个帧长是后端 WebSocket 协议约定好的。

WASAPI 每次回调拿到的数据量是不确定的——取决于声卡缓冲区大小和轮询间隔，可能一次拿 300 字节，下一次拿 900 字节。帧累积器的工作就是把这些零散的 PCM 数据拼成固定的 1280 字节帧再发送。类比 TCP 的"粘包"概念：WASAPI 给的是"流"，帧累积器负责切成"帧"。Buffer 不够 1280 字节就先攒着，够了就切一块发出去。停止采集时，把残留的最后一点强制 flush 出去，标记为 isFinal——保证不丢失任何音频数据。

### 4. 和 Android 端的字节级兼容

桌面端的 PcmNormalizer（TypeScript）和 Android 端的 PcmNormalizer（Kotlin）用的是完全相同的算法——线性插值重采样、立体声转单声道、clamp 防溢出，连浮点运算的精度都通过单元测试对齐。两端归一化后的输出在字节级完全一致，后端收到的帧无法区分来源。这对双端用户的体验一致性很重要——同一个会话里从手机切换到电脑，后端不需要做任何格式转换。

## 四、Wire Protocol 自定义二进制协议

**简历对应：** "通过自定义二进制 Wire Protocol 发送到后端"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 二进制协议相关名词，原有问答未改动。

- **文本协议 vs 二进制协议**：JSON 是文本协议（人可读、自描述，但要逐字符解析）；二进制协议把字段直接按字节排布（紧凑、解析是固定偏移读取）。实时音视频传输业界清一色二进制（WebRTC/RTP 全是）——音频帧每秒 25 帧持续高频传输，省 40% 带宽 + 省掉全部序列化开销，这个选择值得做。
- **base64**：把二进制编码成 64 个可打印字符，每 3 字节变 4 字符——固定膨胀 33%。JSON 只能装文本，二进制进 JSON 必须先 base64。
- **魔数（Magic Number）**：数据开头的固定标识字节，用途是快速校验"这串字节是不是我期待的东西"。PNG 是 89 50 4E 47、JPEG 是 FF D8 FF、Java class 是 CA FE BA BE、PDF 开头是 %PDF。协议里的 "ACP1" 同理。
- **大小端（Endianness）**：多字节整数在内存/网络中的字节排列顺序。大端 = 高位字节在前（人类读数字的习惯，也是网络字节序，TCP/IP 标准）；小端 = 低位字节在前（x86 CPU 内存里的实际排法）。发送方和接收方必须约定一致，否则 0x00000001 会被读成 0x01000000。本项目统一大端，和后端 Python、Android 默认行为对齐。
- **UUID**：128 位全局唯一标识。JS 的 Number 是 64 位浮点数，精确整数上限 2^53-1，装不下 128 位整数——所以拆成两个 64 位 BigInt 写入。BigInt 是 ES2020 引入的原生任意精度整数类型。
- **DataView**：JS 操作二进制缓冲的 API，可在任意偏移按指定字节序读写数字（getUint8 / getUint32 / getBigUint64，参数指定 littleEndian）。桌面端协议编解码靠它按固定偏移读字段。
- **ByteBuffer**：Java/Kotlin NIO 的二进制缓冲类（默认大端），Android 端协议实现用它。
- **struct**：Python 标准库的二进制打包模块，按格式字符串 pack/unpack（如 ">I" = 大端 4 字节整数），后端协议实现用它。
- **字节级兼容测试**：同一份输入分别丢给三端编码器，断言输出字节数组完全一致（vitest 跑）。协议改动的回归保障——面试讲这个细节很加分。

### 1. 为什么不用 JSON 传音频？

音频不是字符串。PCM 原始数据是二进制缓冲，如果硬要塞进 JSON——先 base64 编码（体积膨胀约 33%），再套上 JSON 的 key、括号、逗号——40 毫秒一帧的 PCM（1280 字节原生）base64 后约 1707 字符，加上 JSON 结构接近 2KB。每秒 25 帧就是 50KB/s 的纯冗余开销。

用二进制协议：44 字节固定头部 + 1280 字节 PCM payload = 1324 字节/帧，比 JSON 方案少约 40% 的带宽消耗。编码和解码也都是原生操作——DataView 或 ByteBuffer 读固定偏移量——不需要 JSON.parse 的字符串解析和对象创建开销。

### 2. 协议结构

协议总共 44 字节固定头，加上可变长度的音频数据体。头部字段依次是：

- **前 4 字节魔数 "ACP1"：** 四个固定的 ASCII 字符。后端拿到字节流，先检查前 4 字节是不是 ACP1——如果不是，说明数据错位了，直接丢弃。作用和 JPEG 的文件头 FFD8、PNG 的 89504E47 一样。
- **版本号（1 字节）：** 当前固定为 1，将来协议升级时用来区分新旧格式。
- **类型（1 字节）：** 区分实时帧（REALTIME）和补传帧（BACKFILL）——断线重连后补传的标记为 BACKFILL，后端知道这是历史数据。
- **来源（1 字节）：** 麦克风还是系统音频。
- **标记（1 字节）：** 当前只用了一个 FINAL 标记，表示这是最后一帧。
- **会话 ID（128 位 UUID）：** 因为 JavaScript 的 Number 最大只能精确表示 53 位整数，处理不了 128 位的 UUID，所以我把 UUID 拆成两个 64 位值——前 16 个十六进制字符转成一个 BigInt（高 64 位），后 16 个字符转成另一个 BigInt（低 64 位）——分别用大端序写入。
- **序列号（8 字节）：** 递增的帧序号，后端用来检测丢包和排序——如果序列号中间跳了一个数，说明丢了一帧。
- **采集偏移（8 字节）：** 发送端时间戳，单位微秒。后端用这个对齐多轨音频（麦克风和系统音频同时采集时做时间同步），也用于计算端到端延迟。
- **负载长度（4 字节）：** 音频数据体的字节数。

所有多字节整数字段都使用 Big Endian（网络字节序），和 Java 的 ByteBuffer 默认行为一致，也和后端 Python 的 struct 模块一致，避免端序混乱。

### 3. 跨端兼容

这条协议在三个地方实现了完全一致的编码和解码：Android 端用 Kotlin 的 ByteBuffer，桌面端用 TypeScript 的 DataView，后端用 Python 的 struct。每次协议改之前都要跑单元测试验证三端的字节级兼容性——把同一份测试数据分别在三端编码，确认输出的字节数组完全一致。

## 五、AI 浮窗 + 隐身模式

**简历对应：** "AI 浮窗功能：独立 BrowserWindow 透明无边框、始终置顶、鼠标穿透，面试/会议场景下悬浮在屏幕角落实时展示 AI 翻译结果；配合 ContentProtection API 实现隐身模式，屏幕共享时窗口内容不可见"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 窗口相关 API 的作用说明，原有问答未改动。

- **transparent / frame / backgroundColor**：transparent=true 让窗口背景可透明（Windows 上依赖 DWM 桌面合成），配合全透明 backgroundColor 和 CSS 内容区域，视觉上就是"只有内容悬浮在桌面上"；frame=false 去掉系统标题栏和边框，代价是窗口拖拽要自己实现（自绘标题栏可用 CSS 的 -webkit-app-region: drag）。透明窗口渲染成本比普通窗口高，浮窗内容要克制。
- **alwaysOnTop**：窗口 Z 序层级设定——OS 层面把窗口放到普通窗口之上，不被遮挡。多个置顶窗口之间仍按正常 Z 序排列。
- **skipTaskbar**：窗口不出现在任务栏——浮窗是辅助展示，不该占一个任务栏位置。
- **setIgnoreMouseEvents(true, { forward: true })**：鼠标穿透。Windows 底层对应 WS_EX_TRANSPARENT 扩展窗口样式——鼠标事件落到浮窗下面的窗口，用户不挪浮窗也能直接操作背后应用。forward=true 时窗口自己仍能收到 mousemove，可以做 hover 效果，但拿不到 click。
- **setVisibleOnAllWorkspaces**："工作区"是 macOS 的概念（Spaces，Mission Control 的多个桌面），加 visibleOnFullScreen 后全屏应用（PPT 演示）上方也可见。
- **SetWindowDisplayAffinity / setContentProtection**：Windows API，控制窗口在屏幕捕获中的可见性（对应 WDA_EXCLUDEFROMCAPTURE）——共享软件抓取该区域时显示纯色。Electron 封装成 setContentProtection(true)；macOS 上对应 NSWindow sharingType 机制。副作用：开启后用户自己截图也截不到这个窗口。
- **独立渲染进程**：浮窗是第二个 BrowserWindow = 第二个渲染进程、第二份 React 应用实例——和主窗口完全隔离，数据只能经主进程 IPC 分发（呼应第一节的问题 4）。

### 1. 浮窗是什么场景用的？

用户开着视频会议（Zoom、腾讯会议、飞书），AI 把对方说的话实时转写并翻译。主窗口太大太明显，需要一个又小又隐蔽的悬浮窗，放在屏幕角落，用户瞄一眼就能看到翻译结果。关键是——对方通过屏幕共享看不到这个窗口的内容。

### 2. 浮窗的技术实现

浮窗是一个独立的 BrowserWindow，配置了几个关键属性：

- **透明无边框：** `transparent: true`, `frame: false`, `backgroundColor` 设为完全透明的黑色。窗口本身没有标题栏和边框，只有 CSS 渲染出来的内容区域可见
- **始终置顶：** `alwaysOnTop: true`，浮窗始终在所有普通窗口上面，不会被遮挡
- **不出现在任务栏：** `skipTaskbar: true`
- **鼠标穿透：** `setIgnoreMouseEvents(true, { forward: true })`，点击浮窗区域时事件穿透到下面的窗口——用户不需要移动浮窗就能直接操作浮窗后面的应用。forward 参数确保鼠标移动事件也能正常穿透
- **全工作区可见：** `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })`，全屏应用（比如 PPT 演示）上面也能看到浮窗

### 3. ContentProtection 隐身

`win.setContentProtection(true)` 是 Electron 把 Windows 底层的 `SetWindowDisplayAffinity` 接口封装了。开启后，屏幕共享软件抓取这个窗口区域时显示的是纯黑或纯白——对远程面试官来说那个位置什么都没有。这个状态在主进程中用一个布尔变量统一管理，切换时遍历所有窗口（主窗口和浮窗）同时设置。

### 4. 数据怎么传到浮窗？

浮窗是独立的 BrowserWindow，有自己独立的渲染进程。数据通过主进程的 AudioCaptureManager 统一分发——同时调用 mainWindow.webContents.send 和 overlayWindow.webContents.send，两个窗口各自监听同一个 IPC 通道。浮窗内的组件收到数据后渲染流式文本，和主窗口的对话气泡展示逻辑独立运行，互不影响。

## 六、LibreOffice 文件转换 + 自动下载器

**简历对应：** "对接 LibreOffice CLI 实现本地离线文件转换，覆盖 Word→PDF、PDF→Word，用 spawn 管理子进程超时与进程树清理，处理 Windows 中文文件名编码兼容问题，支持 LibreOffice MSI 安装包自动下载（断点续传/暂停）及本地安装包导入"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** LibreOffice/下载器相关名词，原有问答未改动。

- **LibreOffice / soffice**：开源办公套件（对应 Word/Excel/PPT）。soffice 是它的命令行入口，`--headless --convert-to pdf` 在无界面模式下跑转换。选它的核心是**本地排版引擎**：Word/PDF 的复杂排版（表格、分栏、页眉页脚）只有真正的排版引擎能还原，纯 JS 库画不出来。
- **spawn**：Node child_process 模块的 API，创建子进程执行外部命令，流式拿输出。和 exec 的区别：spawn 输出是流（适合 LibreOffice 这种可能刷大量日志的进程），exec 把输出缓冲进内存（适合一次性小命令）。
- **taskkill**：Windows 命令行杀进程工具。/F 强制终止（不等待进程自己退出）、/T 终止整个进程树（连同子进程）、/PID 指定进程号。
- **SIGTERM / SIGKILL**：Unix 信号。SIGTERM（15）= "请你退出"，进程可捕获并清理资源；SIGKILL（9）= 内核直接终止，进程无法拦截，是最后兜底。
- **进程树 / 孤儿进程**：只杀父进程时，子进程会脱离父进程继续存活（孤儿进程），占用资源还锁着文件。所以任务要按"整棵树"清理。
- **MSI**：Windows Installer 的安装包格式，由 msiexec.exe 执行（/qn = 完全静默安装）。本质是 **OLE2 复合文档**——一个文件里塞多个"流"的容器格式（.doc/.xls 同款容器），文件头 8 字节固定魔数 D0 CF 11 E0 A1 B1 1A E1，因此能校验文件真伪。
- **msiexec 退出码**：数字码表（1602 用户取消、1603 致命错误、1618 已有安装在进行、1625 需管理员权限……），映射成中文提示是产品化细节。
- **HTTP Range**：HTTP/1.1 标准字节范围请求（RFC 7233）。请求头 `Range: bytes=5000-` = "从第 5000 字节开始发"，服务器回 206 Partial Content。所有下载工具的断点续传都是这个机制。
- **指数退避**：重试间隔按倍数递增（1s→2s→4s）。更工程化的做法还会加随机抖动（jitter），避免一批客户端在同一瞬间同时重试。项目是"镜像轮换 × 每源退避 × 全局失败兜底"三层容错。
- **GBK / 命令行编码**：Windows 命令行参数的编码（GBK 代码页）和程序内部编码（UTF-8）不一致时，中文路径在传递中被错误解读。绕过思路：让命令行只出现 ASCII（复制到临时目录转换）——不修编码，修输入。
- **VC++ 运行库 / 合并模块**：MSVC 编译的程序运行时依赖几个 DLL（vcruntime140.dll、vcruntime140_1.dll、msvcp140.dll，"140" 对应 VC++ 14.x 工具链）。合并模块（merge module）是 MSI 里嵌入共享组件的安装单元；静默安装跳过合并模块时 DLL 缺失，补 DLL 是标准修复手段。

### 1. 为什么不调后端 API 做转换？

**离线可用。** 用户可能在面试现场没有网络，或者网络受限（公司内网、VPN）。文件本身也是隐私数据——合同、评估表、技术方案——不上传到远程服务器更安全。LibreOffice 渲染引擎在本地跑，文件从头到尾不出本地磁盘。

### 2. 为什么选 LibreOffice？

对比下来，LibreOffice 是唯一同时满足"离线 + 免费 + 双向转换（Word↔PDF）+ 复杂排版效果好"的方案。Microsoft Office 效果最好但需要付费授权，而且 Office 本身不原生支持 PDF 转 Word。pdf-lib 和 pdfjs 这类纯 JS 库只能生成简单 PDF，遇到复杂表格、多栏布局、图文混排效果很差。后端 PyMuPDF 效果好但需要网络调后端——和我们"离线优先"的目标冲突。

### 3. spawn 管理的细节

**进程超时问题：** LibreOffice 转换大文件可能需要几分钟。我用 5 分钟硬超时——到了时间就杀进程。Windows 上用 taskkill 的 `/F` 强制终止，加 `/T` 做进程树清理——soffice.bin 可能 fork 出子进程，只杀主进程子进程会变孤儿进程继续占用资源，`/T` 保证整棵树都被清理干净。macOS 和 Linux 上直接用 SIGKILL 信号。

**Windows 中文文件名问题：** soffice 的命令行参数传中文路径时，Windows 命令行编码（GBK）和 LibreOffice 内部编码不一致，导致解析出乱码、找不到文件。解决思路：检测文件名是否含非 ASCII 字符——如果含，先把文件复制到系统临时目录（路径全是 ASCII），用临时名转换完，再把结果搬回原始目录并改名。这样避开了命令行编码这个坑，而不是试图在编码层面修复。

### 4. 下载器为什么设计了 7 个镜像源？

LibreOffice 官方下载站在国外，国内用户直连可能就几十 KB/s。我列了 7 个镜像按优先级排列：阿里云镜像（国内最快）、腾讯云镜像（备选），然后是台湾、日本、韩国的亚洲镜像，最后是美国和官方源兜底。下载逻辑：从第一个源开始试，失败或太慢就跳到下一个，每个源重试 3 次（指数退避 1 秒、2 秒、4 秒），7 个都失败才报错，最大程度保证在各种网络环境下都能下载成功。

### 5. 断点续传怎么实现的？

把下载进度记录到本地 JSON 文件中，包含下载地址、文件总大小、已下载字节数、临时文件路径。用户暂停时中断 HTTP 请求，临时文件保留在磁盘上。用户恢复时，先读取进度文件，用 HTTP `Range` 请求头告诉服务器从哪个字节开始发——服务器会跳过已下载的部分，从断点处继续传输。下载前还校验一下临时文件大小是否和记录一致（允许 4KB 误差来应对文件系统块对齐），不一致就重新下载，防止文件被意外损坏。

这里没有用 Electron 的专有 API，就是用标准 HTTP/1.1 的 Range 请求头手动实现——这是标准协议的能力，不依赖特定 Electron 版本。

### 6. MSI 安装的坑

**VC++ DLL 补丁：** 静默安装模式可能跳过 VC++ 合并模块的安装，导致 LibreOffice 启动报"缺少 vcruntime140.dll"。解决方法是安装完成后，从系统目录把几个 VC++ 运行时 DLL（vcruntime140.dll、vcruntime140_1.dll、msvcp140.dll 等）复制到 LibreOffice 的 program 目录——每个 DLL 用 try-catch 容错，某个不存在不阻塞其他。

**MSI 文件头校验：** MSI 文件本质是 OLE2 复合文档，有固定的魔术字节。下载完成后校验前 8 字节是否匹配——不匹配说明镜像返回了 HTML 错误页面而不是真实的 MSI 文件，直接报错，防止安装垃圾数据。

**错误码映射：** msiexec 的退出码是数字（1602=用户取消、1603=致命错误、1618=另一安装进行中、1625=需管理员权限），普通用户看不懂。我把这些码翻译成中文提示，让用户知道具体出了什么问题。

## 七、系统托盘 + 全局快捷键

**简历对应：** "系统托盘常驻（最小化到托盘、右键菜单切换浮窗/退出）、全局快捷键（Ctrl+1/2/3 页面切换、Ctrl+B 浮窗、Ctrl+Shift+P 隐身），状态栏展示快捷键提示"

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 托盘/快捷键相关名词，原有问答未改动。

- **系统托盘（System Tray）**：Windows 任务栏右下角的通知区域。程序通过 Win32 API Shell_NotifyIcon 注册图标；Electron 的 Tray 类封装了它——所以托盘是主进程能力（渲染进程碰不到）。macOS 对应菜单栏图标。
- **globalShortcut**：Electron 的全局快捷键 API，底层是系统级热键注册（Windows 上 RegisterHotKey）——**应用不在焦点时也触发**。全局注册天然有冲突问题（Ctrl+B 在浏览器里是收藏夹），且平台行为差异多。项目选择应用内快捷键：只有窗口聚焦时响应，不抢其他应用。
- **keydown**：DOM 键盘事件——页面聚焦时按下键盘触发。事件对象带修饰键布尔值 ctrlKey / shiftKey / altKey / metaKey，组合键解析 = 把这些布尔值拼成字符串查表，纯 JS、跨平台。
- **metaKey**：macOS 的 Command 键（⌘）。Windows 键盘没有 metaKey（Win 键在浏览器键盘事件里不暴露），代码里 `ctrlKey || metaKey` 让 Ctrl 和 Cmd 等价——这就是"跨平台快捷键不用写 if(macOS)"的原因。
- **nativeImage**：Electron 的图像对象（可从文件或内存 buffer 创建图标）。createEmpty() 创建空图标交给托盘——Windows 会用系统默认图标渲染，避免小尺寸图标糊掉（呼应第十节追问）。

### 1. 为什么做托盘？

桌面端辅助工具的核心体验是"无感常驻"。用户不会一直盯着主界面——开会的时候、写代码的时候，工具在后台运行，需要的时候切出来看一眼。托盘让应用最小化到通知区域，不占任务栏空间，随时能右键唤出菜单。双击托盘图标恢复主窗口。

### 2. 全局快捷键的注册方式

我没有用 Electron 的 globalShortcut API——那个是系统级全局注册，可能和其他应用的快捷键冲突（比如 Ctrl+B 在浏览器里是收藏夹）。我采用的是渲染进程的 keydown 事件监听加自定义组合键解析：把 ctrlKey、shiftKey、altKey 和 key 拼接成组合键字符串（比如 "Ctrl+Shift+P"），然后查表调用对应的处理函数。

**好处：** 焦点在应用窗口内时才响应，不会干扰其他应用的同款快捷键。解析逻辑纯 JS 实现，跨平台——macOS 上 Cmd 键自动对应 metaKey，不需要特殊处理。

### 3. 状态栏的作用

底部的状态栏不是装饰——它展示所有可用快捷键，降低用户的学习成本。功能做得再强，用户不知道就相当于没做。

## 八、音频采集的完整数据流

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 数据流里的名词，原有内容未改动。

- **ASR（自动语音识别）**：把音频流转成文字的服务，后端的第一道处理（"语音转文本"）。
- **LLM（大语言模型）**：生成式模型，这里承担翻译和面试问答生成，输入是 ASR 转出的文本。
- **wss**：WebSocket over TLS——加密的 WebSocket（类比 https 之于 http）。生产环境必走 wss，音频内容是隐私数据。
- **事件分发（fan-out）**：主进程一条事件同时发给多个窗口——AudioCaptureManager 发一次，各窗口 webContents.send 各送一份，消费端完全解耦。

用一个总览来串起上面所有模块：

1. **Windows 声卡混音** → 各种音源混合后的音频信号
2. **WASAPI Loopback C++ 插件** → 每 10 毫秒轮询一次，拿到 48kHz 立体声浮点 PCM，过滤静音帧，通过 ThreadSafeFunction 跨线程回调到 Node.js
3. **PCM 归一化器** → 线性插值重采样到 16kHz，立体声转单声道，浮点转 16 位整数
4. **帧累积器** → 把零散的 PCM Buffer 攒够 1280 字节（40 毫秒一帧），切成标准帧
5. **Wire Protocol 编码** → 给每帧加上 44 字节固定头（魔数 ACP1、UUID、序列号、时间戳）
6. **渲染进程 WebSocket** → 通过 wss 连接发送编码后的二进制帧到后端
7. **后端 ASR + LLM** → 语音转文本，翻译成目标语言
8. **主窗口 + 浮窗** → 双向分发：主窗口展示完整对话气泡，浮窗展示最新翻译结果（隐身保护）

## 九、WebSocket 断线重连与会话恢复

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** WebSocket 相关名词，原有问答未改动。

- **WebSocket**：基于 TCP 的全双工长连接协议。用一次 HTTP Upgrade 握手把连接"升级"成双向通道，之后双方随时互发消息，帧头只有几字节。和 HTTP 轮询比：不用每 40ms 发一个带完整 HTTP 头的请求，开销低、延迟低；和 SSE 比：SSE 只能服务器→客户端单向，推音频需要双向。**持续高频小包上传是 WebSocket 最典型的适用场景。**
- **关闭码（Close Code）**：WebSocket 关闭帧里的 16 位状态码。1000 = 正常关闭；1006 = 异常断开（网络断了收不到关闭帧，浏览器替你填 1006）。判断"该不该重连"就是看这个码。
- **client_hello → ready 握手（补充细节）**：连接建立后客户端先发 client_hello（协议版本、客户端类型），服务端回 ready 之后才认为"连接可用"——比"TCP 连上就算数"可靠，因为连上不一定通过鉴权。代码里 connect() 收到 ready 才 resolve。
- **竞态条件（Race Condition）**：多个异步事件到达顺序不确定导致状态错乱——比如旧连接的 onclose 晚于新连接的 onopen 到达。generation 快照就是给每个回调贴"属于哪个连接版本"的标签。

### 1. 断线检测

桌面端 WebSocket 放在渲染进程，使用浏览器原生的 WebSocket API。断线通过 onclose 事件检测——关键判断是关闭码：1000 是正常关闭（用户主动停止），任何非 1000 的关闭码都视为异常断开，需要触发重连。用户主动调用 disconnect 时，先把重试计数器设为最大值，再调用 close(1000)——双重保险，确保主动断开不会误触发重连。

### 2. 重连策略：指数退避

最多重试 10 次，延迟公式是 500 毫秒 × 2 的 n 次方，但最长不超过 30 秒。所以重连间隔序列是：500ms → 1s → 2s → 4s → 8s → 16s → 30s → 30s → 30s → 30s。总重连窗口约 2.5 分钟。

**为什么选 10 次而不是无限？** 如果网络真的长期不可用（飞行模式、VPN 断了），无限重试只会浪费电量和带宽。10 次覆盖了绝大部分短暂断网场景——WiFi 切换、电梯、隧道。超过 10 次标记为"dead"状态，UI 显示重试按钮让用户手动介入。

**为什么指数退避而不是固定间隔？** 如果断连是因为服务端临时过载，固定间隔会让所有客户端同时蜂拥回来重连，加剧过载。指数退避让重连间隔逐渐拉长，给服务端恢复时间，也避免了雪崩效应。

### 3. generation 防竞态

每次建立新连接时，递增一个 generation 计数器，并把当前值快照下来。所有异步回调（onopen、onmessage、onclose、onerror）在入口处检查：如果回调里的 generation 和最新的不一致，说明这个回调来自一条已被替代的旧连接，直接忽略。

这个机制防止一种典型竞态：连接 A 的 onclose 触发了重连，创建了连接 B（generation=2），但连接 A 的某些回调延迟到达（操作系统网络栈缓冲中）——如果不检查 generation，就会把旧连接的过期消息错误地当作当前会话数据处理。

**为什么只在回调入口检查就够了？** 因为这四个事件是所有异步事件的入口，在入口处拦截就覆盖了所有情况，不需要在每个方法内部都检查。

### 4. 重连后的会话恢复

重连不是"从零开始"。如果是采集过程中断线的，sessionId 和当前激活的音轨列表还保留在内存里。重连成功后，自动发送 session_start 消息（带上之前的 sessionId），然后依次发送每个音轨的 track_start 消息（格式参数保持和之前一致：16kHz、16 位、单声道、PCM16 LE、40 毫秒帧长）。后端识别到已有的 sessionId 后恢复内存上下文——ASR 会话、对话历史等——然后继续接收 PCM 帧。用户感知不到这次重连带来的中断。

### 5. 重连期间的 UI 状态变化

状态分为五级，逐级退化：
- **connecting** → 正在建立连接，UI 显示加载动画
- **ready** → 连接正常，绿色状态，正常工作
- **degraded** → 连接不稳定但还能收发，用户正常使用，可能有短暂延迟
- **reconnecting** → 正在重连，UI 显示重连中。自动的，通常几秒内恢复
- **dead** → 重连次数用尽，显示重试按钮——只有这个状态需要用户介入

## 十、可能的追问点

### 0. 本节技术名词速查（补充）

> **【面试速查 · 2026-08-17 补充】** 追问点涉及的名词，原有问答未改动。

- **SetEventHandle / 事件驱动**：WASAPI 的另一种工作模式——注册一个 Windows 事件对象（内核同步原语，HANDLE），缓冲区有数据时系统置信号，采集线程用 WaitForSingleObject 等信号被唤醒，"有数据才醒、没数据就睡"；轮询是定时器主动上门问。事件驱动省 CPU 但线程同步复杂，轮询简单可控——对 10ms/40ms 这个量级，轮询代价完全可接受。
- **BlackHole / Soundflower**：macOS 的虚拟音频设备方案。原理：装一个虚拟驱动，把系统输出"虚拟成一个输入设备"，采集端把它当普通麦克风读。代价：要装驱动、要授权，属于用户侧配置。
- **CoreAudio HAL**：macOS 的音频子系统（对应 Windows 的 WASAPI），HAL = 硬件抽象层，AudioHardware API 是它的编程入口——macOS 原生采集就写在这一层。
- **nativeImage**：见第七节速查。

### Q: 为什么 WASAPI 不用 event-driven 模式而是 polling？

WASAPI 支持事件驱动（通过 SetEventHandle 设一个 Windows 事件对象）和定时轮询两种模式。我选轮询的原因是代码简单、可控性好，不依赖 Windows 事件对象的线程同步。10 毫秒轮询间隔对 40 毫秒帧周期来说精度完全够——最多延迟 10 毫秒拿到数据，不会造成丢帧。

### Q: 帧长为什么选 40ms 而不是 20ms 或 60ms？

和后台商量后定的。20 毫秒帧意味着每秒 50 帧，WebSocket 发送频率过高，网络开销大，后端处理压力也大。60 毫秒帧延迟感明显——用户说完话要等 60 毫秒才有一帧数据到达后端。40 毫秒（每秒 25 帧）是延迟和效率的最好平衡。

### Q: 如果 WASAPI addon 加载失败怎么办？

C++ 插件的 require 被 try-catch 包裹，加载失败不会 crash 整个应用。降级方案是只用 Web Audio API 做麦克风采集，系统音频不可用但核心功能（翻译）还能正常工作。这也是为什么设计上麦克风和系统音频是两条独立的采集路径——一条挂了不影响另一条。

### Q: macOS 上系统音频怎么采集？

WASAPI 是 Windows 专有的。macOS 可以用 BlackHole 或 Soundflower 虚拟音频驱动，或者用 CoreAudio 的 HAL Output。目前 WASAPI addon 是 Windows 专属的，但架构上 audio-capture.ts 的接口是平台无关的——start(source)、stop()、EventEmitter 事件——底层实现可以替换。macOS 版可以在条件编译中替换为对应的原生方案，上层业务代码不需要任何改动。

### Q: 为什么系统托盘图标用空的 nativeImage？

Windows 托盘区域很小，一个精细的 App icon 缩小到 16×16 像素会糊成一团。用 createEmpty 配合 Windows 系统渲染自动绘制默认图标，简洁够用。功能正确性比图标完美更重要。

### Q: 多窗口的 ContentProtection 状态如何保持同步？

主进程中一个布尔变量统一管理。切换时遍历所有窗口同时设置。新建窗口不会自动继承隐身状态，创建后需要额外调一次。当前实现不持久化——每次启动默认关闭，用户手动开启。

## 十一、和移动端的对比（面试官可能会问）

|------|------------|------------------|

| 麦克风采集 | Kotlin AudioRecord | Web Audio API (浏览器API) |

| 窗口管理 | 无（全屏 App） | 多窗口 + 浮窗 + 托盘 |

| PCM Normalizer | ✅ Kotlin 版 | ✅ TS 版（等价算法） |
| 状态机 | useReducer | useReducer（从 RN 零改动迁移） |

两端共享：同一套后端、同一套 Wire Protocol、同一套 interviewReducer 状态机逻辑（桌面端的 interview-reducer.ts 标注了"从 RN 零改动迁移"）。

### 补充：对比表名词速查（2026-08-17）

> **【面试速查 · 2026-08-17 补充】** 表格涉及移动端名词，被问"移动端怎么做的"时用。

- **React Native（RN）**：用 React 写原生移动应用——JS 描述界面，通过桥调用原生组件渲染。移动端用它，所以面试会话状态机（useReducer 纯逻辑）能零改动搬到桌面端。
- **Kotlin**：Android 官方语言，跑在 JVM 上。移动端原生层（AudioRecord / MediaProjection / PcmNormalizer）用它写，对应桌面端的 C++。
- **AudioRecord**：Android 的麦克风采集 API，直接拿 PCM 帧。
- **MediaProjection**：Android 的系统级捕获 API（Android 10+），带用户授权弹窗，可捕获屏幕和系统内部音频——移动端系统音频的来源。
- **useReducer**：React 状态管理 Hook：dispatch(action) → reducer 纯函数(旧状态, action) → 新状态。适合状态机式流程——面试会话就是典型状态机（采集/推流/转写/回答各状态互斥转换）。纯函数 = 可迁移、可单测。
- **Tailwind CSS**：原子化 CSS 框架——直接在 className 写工具类（bg-white、px-4），不写独立样式文件，桌面端 UI 用它快速搭界面。
